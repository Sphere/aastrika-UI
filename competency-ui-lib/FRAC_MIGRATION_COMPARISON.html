Competency Data Migration: Static JSON → FRAC Service

competency-ui library (@aastrika_npmjs/comptency) · Before vs Now comparison

In one line: The competency dashboard used to read one big static JSON file. It now reads live data from the FRAC service — the same information, but always up to date and split into small, purpose-built API calls.

1. Where the data comes from

public/v8/competencyAssets/roleWiseCompetencyData		 FRAC service (live)
proxies/v8/entity/v1/hierarchy + entity/v1/search

2. How one competency page loads

BeforeNow
1. Download the entire role/competency JSON (all positions).
2. Download the rolesMappingData JSON.
3. In the browser, find the row matching the user's designation.
4. Show roles, activities, competencies and the self-assessment courses. 		1. search(Position) → find the user's designation → its FRAC code (e.g. ANM/MPW → P10).
2. hierarchy(P10) → that position's roles → activities → competencies (with levels).
3. search(Competency) → get each competency's real number.
4. Show the same screen — roles, activities, competencies, courses.
The screen looks and behaves the same to the end user. Only the data plumbing behind it changed.

3. The tricky part: the competency identifier

This was the one real gotcha, and why the page briefly showed "no result found" during the switch.

 Before (JSON)FRAC first attempt
Competency is identified by a number → 100 a code → C1
Courses are tagged with 100 (number) → MATCHED 100 (still number) → C1 matched NOTHING
Result Courses appeared under the competency Empty "Required" tab → "no result found"

The fix

FRAC's entity/v1/search returns both the code and the real number:

{ "code": "C1", "entityId": "100", "name": "Pregnancy Identification", ... }

So we now translate each competency's code back to its real number (C1 → 100) before showing it. Courses, progress bars and the passbook all match on that number again — exactly like before.

Why it matters: the number (entityId) is the "real id" the rest of the platform (courses, progress, passbook) has always used. FRAC's structure uses codes, so we map code → number in the middle. Newer positions (like ANM_UP) already use codes end-to-end, so they map to themselves and keep working too.

4. Finding the position code

Before (interim)Now
The designation → position-code list (ANM/MPW → P10) was hardcoded in the library — fragile, and would break for new positions. Pulled live from search(Position), which returns all positions with their codes and names. The hardcoded list is now only an offline safety net.

5. Language: two calls became one

BeforeNow
Fetched the hierarchy twice — once in English, once in Hindi — so the page could switch language on the fly. The language is already known from the app (eagle-fusion root config), so we fetch the hierarchy once in that language. One less network call per tab.

6. API endpoints — removed vs added

StatusEndpointPurpose
REMOVED public/v8/competencyAssets/roleWiseCompetencyData Old static role/competency tree (all positions)
REMOVED public/v8/competencyAssets/rolesMappingData Old designation → roleId map (its result was unused dead code)
ADDED proxies/v8/entity/v1/hierarchy One position's full tree: Roles → Activities → Competencies + levels
ADDED proxies/v8/entity/v1/search (Position) Designation → position code lookup
ADDED proxies/v8/entity/v1/search (Competency) Competency code → real number (entityId) lookup

Unrelated endpoints (user profile read, course search, passbook, progress) are unchanged.

7. Net result

  • Same experience for the user — the Job Description, Passbook and Required tabs look and work the same.
  • Live data — no more stale hand-maintained JSON files.
  • Lighter — a few KB per position instead of a ~12 MB whole-file download.
  • Fewer calls — one hierarchy call per tab instead of two (English + Hindi).
  • Nothing hardcoded — positions and competency numbers are resolved live from FRAC.
  • Works for all positions — legacy (number-based) and newer (code-based) alike.
